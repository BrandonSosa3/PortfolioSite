Regulist - Technical Deep Dive

Role: Co-Founder & Sole Engineer — built the entire two-sided marketplace single-handedly. Now in launch phase with 20 agencies and 75 businesses on the pre-launch waitlist.

Challenge: Freelance marketplaces typically handle simple one-off payments, but professional service contracts require multi-party signing workflows, flexible payment structures, and enforceable cancellation logic — all without exposing clients to payment processing complexity.

Solution: Built a full-stack B2B marketplace with dual buyer/seller portals, a tiered Stripe Connect payout system, and a contract engine supporting three payment schedule types (one-time, installments, milestones) with mutual cancellation and modification flows.

System Architecture:

• Dual Portal System: Separate dashboards for buyers (project posting, proposal review, contract signing) and sellers (verification, proposals, portfolio, subscription management)
• Contract Engine: Three-schedule payment system with per-payment Stripe PaymentIntents, idempotency keys, and status state machines (pending → signed → paid → cancelled)
• Tiered Platform Fee: Fee rate locked at contract signing time (Free 12% → Elite 6%), stored in the contract record so rate changes never affect active agreements
• APScheduler Jobs: Automated installment charging, 48-hour advance payment reminders, and overdue milestone alerts — all idempotent with per-row notification flags to prevent duplicate sends
• Admin Portal: Full audit trail, seller verification queue, manual credit adjustment, analytics, and TOTP-based MFA
• Subscription Billing: Stripe Connect subscriptions with proration logic — immediate mid-cycle upgrades, end-of-period downgrades — plus webhook-driven handling of downgrades, cancellations, and failed payments
• Production Hardening: JWT refresh-token auth, API rate limiting, password strength validation, AWS S3 document storage with filename sanitization, and a compliant account-deletion flow that preserves executed contracts for legal retention

User Workflow:

Seller Side:
1. Sign up, submit verification documents (uploaded to S3)
2. Select subscription tier (Basic / Pro / Elite) once approved
3. Browse buyer projects, spend credits to initiate conversations
4. Submit proposals with one-time, installment, or milestone payment schedules
5. Sign contracts; receive payouts via Stripe Connect with Regulist platform fee deducted

Buyer Side:
1. Sign up, post projects with service types and budget
2. Review seller proposals, negotiate via in-app messaging
3. Schedule meetings (Zoom / Google Meet) directly in the conversation thread
4. Sign contracts; card charged automatically per schedule (one-time on signing, installments on due dates, milestones on approval)
5. Rate sellers on Regulist-verified campaigns only (auto-created on payment)

Key Differentiator: Unlike standard freelance platforms with single flat payments, Regulist enforces structured contract lifecycle management — proposals require mutual signing before any charge, installment cancellations take effect at the billing period boundary rather than immediately, and milestone submissions are gated on buyer approval before Stripe capture — giving both parties legally consistent, auditable records.

Campus Run - Technical Deep Dive

Role: Co-Founder & Software Engineer — sole engineer on a four-person startup, owning the entire production stack: architecture, database design, backend, admin interface, authentication, CI/CD, and DNS. 20 API routes, 13 PostgreSQL tables across 8 migrations, 60 passing unit tests.

Challenge: A brand that sponsors a campus activation — a sampling table, a giveaway, a booth — spends real money on product and staffing and gets back an anecdote. Nobody can say which table, which hour, or which campus produced a customer. The standard capture tools make it worse: a paper signup card is a transcription problem, and a QR pointed at a generic form drops most of the people who touch it and still cannot connect them to a purchase. The hard part isn't the landing page; it's carrying identity across the gap between a physical moment outdoors and a redemption in a store days later.

Solution: Built the attribution layer that closes that gap, implementing Apple's PassKit Web Service protocol end to end. A tap issues a cryptographically signed wallet pass unique to that person and that event, and the pass stays on their phone as the identity carrier — through the wallet add, through the link click, through to in-store redemption. The result is a five-stage funnel recorded on an append-only event store, delivered to brand partners as post-campaign reports with coupon redemption and engagement analytics.

System Architecture:

• PassKit Web Service, End to End: Dynamic per-card pass generation with cryptographic signing, plus authenticated device callback endpoints using constant-time token comparison — so registration and update callbacks from Apple's servers can't be forged, and token checks don't leak via timing
• Five-Stage Attribution Funnel: tap → wallet add → link click → in-store redemption, recorded on an append-only event store. Append-only matters: stages are observed facts that never get rewritten, so a report can be recomputed from history rather than trusted as a running tally
• Hostile-Conditions Capture Path: The capture flow runs outdoors on strangers' phones with unreliable connectivity. An offline-resilient retry queue absorbs dropped requests, and telemetry is moved off the critical response path so a database failure costs an analytics row, never a user their coupon
• Idempotent Pass Issuance: Pass issuance is keyed on HMAC-derived tokens, so a retry, a double-tap, or a queued request replayed after a reconnect yields the same pass instead of a duplicate — the property that makes the retry queue safe to have
• Designed for Burst Load: Built for 1,000–3,000 taps inside a 3–4 hour activation window, where the traffic is a spike against a hard deadline rather than a steady curve, and a failure during the window can't be retried later
• Full Stack Ownership: 20 API routes and 13 PostgreSQL tables across 8 migrations, with authentication, an admin interface, CI/CD, and DNS all owned by one engineer and covered by 60 passing unit tests

Correctness & Security Work:

• Caught a client-facing reporting defect that could report conversion rates above 100%. Android users redeem without ever adding a wallet pass, so a rate based on passes issued had a denominator that undercounted the people actually reached. Re-based every rate on distinct people reached — a defect worth finding precisely because the number was going into reports handed to paying clients
• Eliminated an open-redirect vector by resolving all destinations server-side rather than trusting a client-supplied target — the relevant class of bug for a product whose entire surface is short links handed to strangers

User Workflow:

1. Capture: A tap at any table, booth, or handout issues a signed wallet pass to the attendee's own phone in one step
2. Opt In: They join the list and answer a question or two, with an optional A/B test on messaging
3. Watch Live: Signups, answers, and best-performing spots stream to a dashboard during the event, so staffing can move to what's working
4. Attribute: The funnel resolves taps through to in-store redemptions, and brand partners receive post-campaign reports with redemption and engagement analytics

Good Company: A format built on the platform — a brand sponsors a lunch, a sorority chapter brings the turnout, and a local retirement home fills with students for an afternoon. The chapter gets volunteer and fundraising hours, the residents get company, and the brand puts product into the hands of exact-fit customers attached to something genuinely worth doing. The same attribution layer reports who came, who opted in, and what it drove.

Key Differentiator: The activation is the surface; the attribution underneath is the product. Agencies sell the event and report impressions — a number that cannot be tied to a person or a purchase. Campus Run carries a signed identity from a tap outdoors through to a redemption in a store, and because one team builds the software and staffs the event, the data layer and the people handing out product are never two vendors pointing at each other when the numbers come back thin. Shipped across three brand activations on five-figure client contracts.

NutritionScanner - Technical Deep Dive

Try it: nutritionscanner-production.up.railway.app — no signup required. The sign-in screen has a "Look around the demo" button that opens a real account with real receipts in it.

Challenge: Nutrition tracking apps depend on manual logging, which people abandon within weeks, and frame everything as restriction — calories, deficits, targets. Grocery receipts are a passive data source that requires no logging discipline, but they're written in a compressed dialect no database indexes: GG ORG BAN 6CT is six organic bananas. An LLM will resolve that line confidently whether or not it's right, and a nutrition total assembled from confident guesses is worse than no total at all.

Solution: Built a five-stage replayable pipeline that transcribes receipts with Claude vision, resolves cryptic line items against USDA FoodData Central through a separately-evaluated LLM pass, and reports what a week's groceries contain and what each nutrient costs — surfacing every unresolved line for correction rather than filling the gap with a guess.

System Architecture:

• Replayable Pipeline: Five stages — extract → normalise → reconcile → resolve → derive. Raw extraction JSON is persisted permanently, so every downstream stage can be re-run against a revised prompt or a corrected mapping without re-photographing or paying for vision a second time. Ingestion is idempotent on image hash; re-uploading updates rather than duplicates
• Measured Resolver: The one component that can be confidently wrong gets a held-out labeled test set and a tracked accuracy number. The eval harness shipped alongside the resolver, not after it — resolution accuracy is a measured figure, not an assumption
• Arithmetic Reconciliation: Line items are summed against the receipt's printed subtotal, tax, and total. A basket that doesn't reconcile is flagged suspect with a specific reason and never silently persisted as clean
• Compounding Correction Loop: Every user fix is stored as a permanent mapping and applied to all future receipts. Correcting GG ORG BAN once means it resolves correctly forever — this is the core product loop, not a settings screen
• Two-Tier Spend Guards: A global monthly ceiling caps total API spend; a per-account receipt quota caps any one account's share of it. Without the second, the first is first-come-first-served — one enthusiastic visitor exhausts the budget and locks out everyone including the owner. Every LLM call logs model, tokens, latency, and cost
• Barcode Rating Engine: Open Food Facts lookup by barcode with per-ingredient hazard classification sourced to IARC and EFSA, scoped and quoted so a contested classification is shown as contested rather than asserted
• Multi-Account Isolation: Private data is scoped by user_id; food, product, and store rows are a shared reference cache. An owner role gates the destructive reference-data operations — merging duplicate foods, overriding a USDA match — so one account can't reshape the catalogue for everyone

User Workflow:

Capture:
1. Photograph one receipt a week — live camera on mobile, file picker on desktop
2. Pipeline extracts, normalises units, reconciles totals, and resolves lines to foods
3. Coverage is reported in the headline — a basket where 60% of lines matched says so prominently

Correction:
1. Unresolved and low-confidence lines are surfaced in a phone-shaped, keyboard-free correction flow
2. Ambiguous quantities prompt for the unit the label actually prints, not a normalised one
3. Each fix is stored permanently and applied to every future receipt

Analysis:
1. Weekly nutrient totals with per-nutrient adequacy against goals
2. Cost-per-nutrient breakdown — what a gram of protein actually costs across a shop
3. Spending organised by line item rather than by receipt
4. Barcode scanning for per-product ingredient ratings and organic classification
5. CSV export with a tested restore path

Key Differentiator: Unlike nutrition apps that require daily logging and frame results as intake and restriction, NutritionScanner reports supply — what was bought, never what was eaten — because a receipt cannot know consumption, and copy implying otherwise is treated as a bug rather than a wording preference. It never fabricates a value to complete a total: unresolved items are surfaced for correction, uncertainty is stated in the headline rather than a footnote, and a visibly incomplete number is treated as correct where a fabricated complete one is not.

Bike Share Demand Forecasting - Technical Deep Dive

Challenge: Urban bike share systems need accurate demand forecasting to optimize bike distribution and operational efficiency across city networks.

Solution: Developed a Random Forest regression model using 2 years of historical data (17,379 hourly records) from Washington DC's Capital Bikeshare system, achieving 67% prediction accuracy (R² = 0.667) with RMSE of 127 bikes per hour.

Key Results:

• Hour of day accounts for 48.6% of predictive power
• Weekday commuters are 5x more weather-resistant than weekend riders
• Rush hour periods show 3x baseline usage
• Clear weather averages 206 bikes/hour vs 62 during heavy rain
• 48-bike improvement over linear regression baseline

Technical Implementation:

• Data pipeline with Kaggle API integration
• Feature engineering for weather comfort indices and temporal indicators
• SQLite database with SQLAlchemy ORM
• Interactive Streamlit dashboard with Plotly visualizations
• Time-aware train/test split validation

CoLiv - Technical Deep Dive

Challenge: Traditional property management systems track properties at the unit level, but co-living spaces require room-level granularity with individual pricing, tenant profiles, and roommate compatibility matching.

Solution: Built a dual-portal system with separate interfaces for operators and tenants, featuring room-level tracking, individual pricing management, and an AI-powered roommate matching algorithm currently in development.

System Architecture:

• Operator Portal: Full property management from properties → units → rooms → tenants
• Tenant Portal: Personal dashboard with room details, payments, and roommate information
• Room-Level Tracking: Each room has individual pricing, size specifications, and tenant profiles
• AI Roommate Matcher: Algorithm in development for lifestyle-based compatibility matching

User Workflow:

Operator Side:
1. Create operator account at co-liv.vercel.app
2. Add property with address and details
3. Create units within the property
4. Define rooms with pricing and specifications
5. Add tenants with credentials
6. Monitor occupancy and manage operations

Tenant Side:
1. Receive credentials from operator
2. Login at co-liv-tenant.vercel.app
3. View room details and amenities
4. Access payment information
5. Connect with roommates
6. Submit maintenance requests

Key Differentiator: Unlike competitors that stop at unit-level management, CoLiv provides granular room-level control, giving operators complete visibility and flexibility across their co-living properties.
